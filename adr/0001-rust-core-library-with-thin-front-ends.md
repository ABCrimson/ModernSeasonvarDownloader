# ADR-0001 — Rust core library with thin CLI and Tauri front ends

Date: 2026-08-22 · Status: accepted

## Decision
All scraping, decoding, searching, downloading, persistence and settings live in one pure-Rust library crate, `seasonvar-core`, with no Tauri dependency. Two binaries consume it: `seasonvar` (CLI, clap) and the Tauri 2 desktop app (commands/events over the core). The React UI never performs HTTP or filesystem I/O.

## Why
- The download engine needs parallel range writes, resume, cancellation and backpressure — a systems-language job; doing it in a webview or a Node sidecar is slower, less robust and harder to test.
- A library with an injectable `base_url` is testable end-to-end against recorded fixtures (`wiremock`) with no GUI; the CLI is a nearly free second front end and the thing CI exercises.
- Keeping I/O out of the webview minimizes the Tauri permission surface (no `plugin-fs`/`plugin-http`).

## Rejected
- **TypeScript engine (Electron or Tauri + Node sidecar):** familiar to the owner, but weaker engine, ~150 MB (Electron) or an extra process (sidecar), and the owner explicitly chose the Rust path.
- **Single Tauri crate:** faster day-one scaffold; entangles engine with runtime, no CLI, harder tests.
- **Web app (Next.js on Vercel):** cannot write to the user's disk; proxying 200 MB CDN files through a hosted server is a poor and costly fit.

## Consequence
Two languages in the repo (Rust + TypeScript); IPC contract generated by tauri-specta so types don't drift; engine bugs are reproducible from the CLI without the GUI.

## Deliberately unresolved
- Whether to publish `seasonvar-core` to crates.io (default: no, path dependency only).
